================================================================

These were open in the 2.20 zip. They are done here. Another programmer
should treat them as closed unless a remaining-issue note says otherwise.

  1. Pension MTD is year-filtered
     closes.index.month == last.month AND year == last.year.
     Simulation (Aug 2026 history): unfiltered MTD = 53 rows across
     2024/2025/2026; filtered = 10 rows in 2026. Forced Flows now
     prints a this-month SPY/TLT gap, not a multi-year gap.

  2. Dump stale fallback
     load_dump_panel catches GitHub failure and serves the local npz
     instead of crashing Top 20 / Lookup / APEX.

  3. recent_ok captured BEFORE close ffill
     Halted/delisted names no longer look "fresh" for five extra
     sessions. Simulation: a name with no print in the last 3 bars
     is False on the pre-ffill mask and True after ffill(limit=5).
     mega_scan / forecast_all / felix / sector_flow / macro_only
     all consume _recent_ok_mask.

  4. history.parquet is aligned on LOAD, not only after a fetch
     A cache written before the weekend fix is cleaned on the way in.

  5. Pressure gauge does not vote "Draining" on missing feeds
     Zero feeds → gauge=None, "Unavailable". Simulation: empty
     components → None; one supportive feed → +1; all three → +3.
     The old default-0 path still votes -3 — that code is gone.

  6. Streamlit cache keys no longer use leading-underscore args
     asof / gauge / override are hashed. A +3 mega_scan is not reused
     at -3.

  7. APEX import failure is scoped to that tab (no st.stop inside tabs)

  8. Best Odds Auto applies the live regime
     _forecast_all(asof, _rk if _apply_macro else None)

  9. Analog rvol is stored uncapped; both sides cap at 3 when matching
     Lookup and universe Odds Up no longer disagree on high-rvol names
     for that reason.

 10. alpaca_prices is chunked (80). Ticker lookup is case-tolerant
     via _ticker_index. forecast_all(only_tickers=) exists.

 11. Alpaca daily history uses adjustment="all".

 12. Unknown fundamentals rank at the bottom, not as average
     (mega_scan quality, Felix, macro-only). Data completeness is shown.

 13. Diversified sector allocation (slot quotas + cap) so one favored
     sector cannot take the whole Top 20. Score itself is NOT multiplied
     by MacroFit — see P1 below, the UI still says it is.

P0-1  APEX "5-factor regime" is 4 factors. Thresholds assume 5.
      File: apex_flow.py score_panel ~156-168
            app.py APEX help + column_config still say "5-factor"

      tally = px>sma20 + px>sma50 + sma20>sma50 + px>sma200
      Missing: sma50 > sma200 (the 5th vote the Pine script / docs
      describe as "MA stack").

      Simulation on synthetic panel:
        4-factor unique tallies = {-4, -2, 0}   (always even)
        5-factor unique tallies  = {-5, -3, -1}   (odd possible)
      STRONG BULL is coded as tally >= 3. With 4 votes of ±1 the
      only way to get >=3 is tally == 4 (unanimous). MILD BULL is
      tally == 2 (exactly 3-of-4). NEUTRAL is 2-2. You can never
      land on the odd buckets the labels were written for.

      This changes the 15-point regime component, therefore Score,
      therefore Gate (Score >= 80). Adding the 5th factor WILL
      change scores vs this zip — do it on purpose, or retitle
      everything to 4-factor and keep the current numbers.

      Recommend: add sma50>sma200 to match the Pine indicator you
      told users this ranks identically to. Then re-check that a
      known chart still prints the same 0-100. If it already was
      4-factor in Pine, change the UI copy instead — but pick one.


P0-2  APEX intraday stacks last-N bars with timestamps discarded.
      File: apex_flow.py _alpaca_bars (keeps only o,h,l,c,v)
            scan_intraday ~361-369
              T = min(len(frames[s]) for s in names)
              T = max(T, MIN_BARS)
              stack frames[s][key].to_numpy()[-T:]

      Simulation: AAA has 250 bars, BBB has 300.
        T = 250. BBB's last 250 is bars 50..299, not the same clock
        as AAA's 0..249. Relative strength vs SPY is then
        "last 21 prints" of mismatched sessions — a 5-min RS of
        ±3% vs SPY is not a 21-bar contemporaneous test.

      Also: if the shortest series is < 210, T is inflated to 210
      and those symbols are dropped. _alpaca_bars already requires
      MIN_BARS, so the max() is a landmine if that filter ever moves.

      Recommend: keep the bar timestamp. Inner-join on timestamp
      (or asof-align to SPY's index) before stacking. Drop T=max(...).
      Raise in score_panel if T < 210 instead of silently using
      c[-200:] of an 80-row array (see P0-3).


P0-3  score_panel does not require MIN_BARS. SMA200 becomes SMA-whatever.
      File: apex_flow.py score_panel (no T check)
            scan_daily raises if dump < 210; scan_intraday does not
            call that raise — it filters symbols, then scores.

      Simulation: T=80 panel scores without error.
        _coverage = 80/200 = 0.40 so _finalize WILL drop them under
        the liquidity guard — good for the daily path with the guard
        on. If anyone calls score_panel directly, or the guard is
        turned off, SMA200 / coverage / regime are fiction.

      Recommend: `if T < MIN_BARS: raise` at the top of score_panel.


P0-4  Best Odds "limited to the N hottest sectors" is a lie.
      File: app.py recipe line ~1609-1614
            _forecast_all / _forecast_scan calls ~1759-1768
            cascade_engine.forecast_scan ~2248-2270

      The recipe banner is shown for every method except Felix:
        "limited to the {_hot_n} hottest sectors ({_t_lbl})"
      Cascade Score honors _hot_n / _use_flow / the day picker.
      Best Odds does not:
        whole-universe path → forecast_all(regime=...)  no hot filter
        shortlist path      → forecast_scan → mega_scan(top=120)

        (b) lens Off still runs mega_scan(apply_macro=True) because

      Recommend: pass hot_only, flow window, apply_macro into
      forecast_scan / forecast_all. Stop drawing the hot-sector
      clause on methods that ignore it. Don't build the analog
      library twice.


P0-5  fetch_history can overwrite a good parquet with a thin download.
      File: cascade_engine.py fetch_history ~171-175
        if len(closes) < 30 or closes.shape[1] < 3:   # failed
            restore stale
        else:
            closes.to_parquet(LOCAL_HISTORY)

      Simulation: NODES has 81 symbols. Gate is "30 rows and 3
      columns", not "covers most of NODES". A Yahoo fallback that
      returns SPY/QQQ/IWM for 40 days will clobber a 3-year 81-column
      cache. After that, sentinels, ratios, yen-carry, and the
      cascade graph run on a skeleton until someone hits Refresh
      AND the feeds fully succeed.

      Also LAST_HISTORY_SOURCE: if Alpaca returns empty for every
      symbol, the label is "yfinance (Alpaca keys not set)" even
      when keys exist and IEX/rate-limit was the actual cause.

      Recommend: refuse to write parquet unless
        (a) n_cols >= 0.8 * len(NODES)  OR
        (b) n_cols >= stale_df.shape[1]
      and only then. Keep stale otherwise. Fix the source string
      to "Alpaca empty (keys present, feed failed)".


P0-6  History cache can serve Friday's close until Wednesday.
      File: cascade_engine.py fetch_history
        if (pd.Timestamp.today() - df.index[-1]).days <= 4:
            return aligned parquet

      Combined with app.py @_history ttl=3600.
      A Friday close is still "fresh" on Tuesday (3 days) and on
      Wednesday morning (4 days). Live Top 20 / Cascade / regime
      will think it is still Friday after two full sessions.

      Recommend: treat as stale if last bar's date is older than
      the previous completed US session (skip weekends), not "4
      calendar days". Keep the 4-day fallback only for when the
      refetch fails.


P0-7  html.escape is still missing on unsafe_allow_html interpolations.
      File: app.py  (dozens of f-strings into unsafe_allow_html)

      Company names (Yahoo shortName), tickers, sector strings,
      Forced Flow Buy text, cascade source/target names, advisor
      labels, recipe HTML all go in raw.

      This is a Streamlit Cloud app. You do not control Yahoo
      shortName. A name containing </div><img...> will break the
      layout; a name containing <script> is an XSS footgun in any
      browser context that still executes markup Streamlit injects.

      Recommend: one _esc(s) = html.escape(str(s), quote=True) and
      run every interpolated field through it. Forced-flow "Buy"
      strings too.

      Simulation (repress, top=20):
        7 lead sectors including Utilities at tilt 1.00 (neutral)
        quota rounds to 3 each = 21 slots, then truncated to 20.
        Neutral Utilities get the same 3-slot floor as Energy 1.15.

      Recommend:
        - Change the help to match the allocator.
        - Exclude tilt == 1.0 from "leads" (use > 1.0), or they
          steal slots from the thesis.
        - Cap sum(quota) to `top` before picking, not after.


P1-2  Tailwind / fastest_followers correlation is not pairwise-complete.
      File: cascade_engine.py _node_follow_corr ~1796-1817
            fastest_followers ~975-981
        xm = x - nanmean(x)          # over the FULL column
        ym = y - nanmean(y, axis=0)
        corr = nansum(xm * ym) / ...

      Simulation (T=200, second series missing first 80 bars):
        complete series: col-mean corr == pairwise  (Δ ~ 0)
        gappy series:     col-mean = 0.763
                          pairwise  = 0.994
        Δ = 0.23 on a series that is actually almost perfectly
        correlated on the overlapping window.

      This is the cascade TAILWIND pillar (29 points of the
      cascade score) and the "fastest followers" table. Gappy dump
      names (IPOs, recent listings, halt-resume) get a systematically
      wrong follow-corr, then a wrong percentile, then a wrong
      Top 20 rank.

      Recommend: the same pairwise mask already used in
      upstream_drivers (~1307-1315). Vectorize with a validity
      mask (Xm.T @ Ym for counts, zero the invalid products).


P1-3  Edge hit_rate is fully in-sample.
      File: estimate_edges ~307-320
      The Spearman IC screen and the directional hit rate use the
      same trailing window. Live ranking, forecast_board conviction,
      and the backtest's "conv" weight all consume it.

      Walk-forward backtest itself is honest (asof slices to
      asof-horizon; simulation produced 11 periods, excess in both
      halves). The hit_rate NUMBER shown to users is not.

      Recommend: compute hit_rate on the most recent 20-30% of the
      train window held out of the IC screen, or at least print
      n_obs next to every hit % so "8 observations of 75%" is
      visibly weaker than 60 of 62%.


P1-4  US holidays stay in the equity calendar.
      File: _align_to_equity_calendar only drops dayofweek >= 5.

      Simulation: Memorial Day Monday is kept. Caller then ffills
      Friday's SPY onto that row. Impulse 5d / z / IC treat a 0%
      holiday as a real session — the same class of bug weekends
      used to be, just rarer.

      Monday crypto still carries the weekend (and holiday) move
      in one bar; equities don't. BTC vs SPY 5d impulses are not
      the same horizon.

      Recommend: drop rows where SPY (or a majority of non-crypto
      columns) is a ffilled holiday — e.g. require a raw, non-ffill
      print in a core equity column before the row counts as a
      session. Document the crypto Monday lump separately.


P1-5  January reversal card never appears in November.
      File: forced_flows ~655-683

      Simulation:
        today = 2026-11-15, days_ahead=80 → 0 January-reversal rows
        today = 2026-12-15              → 1 row dated 2027-01-05
      In November the event date is date(today.year, 1, 5) =
      2026-01-05 (already past), so the filter today <= Date drops it.

        y = today.year + (0 if today.month == 1 and today.day <= 5 else

P1-8  Sector-flow formula does not implement the 40/25/20/15 mix
      the UI describes.
      File: cascade_engine.py sector_flow ~2916-2917
        flow = 0.40*(ret-mkt)
             + 0.25*(breadth-0.5)*0.10
             + 0.20*tanh(sg-1.0)*0.02
             + 0.15*ret

      Simulation, typical session (+0.6% vs market, 58% up, 1.2x
      dollar volume):
        rs=0.00240  breadth=0.00200  volsurge=0.00079  ret=0.00090
      The extra *0.10 and *0.02 look like leftover unit conversions.
      Volsurge is nearly inert (max contribution ~0.004 even on a
      3x surge). Breadth can rival RS on a quiet day and collapse
      on a 5% day. The validated "+3.41% / 21d" result used THIS
      formula, so changing it changes the backtest — but the caption
      "a sector is hot when money-weighted return, breadth and
      turnover all lean the same way" oversells turnover especially.

      Recommend: either drop the *0.10/*0.02 and re-run the
      walk-forward, or rewrite the caption to "mostly dollar-weighted
      relative return, with a small breadth kicker".

P2-1  No tests in the zip. The v2.19 tree had tests/test_logic.py.

P2-2  Watchlist is data/watchlist.json on the server.
      Streamlit Cloud filesystems are ephemeral and shared.
      Every visitor on a given replica shares one list; a reboot
      wipes it. Caption already warns a little — make it "this
      demo host does not persist a personal watchlist" or move to
      st.session_state / a user store.

P2-3  IEX feed is hardcoded on every Alpaca call
      (snapshots, daily bars, analyzer OHLCV, APEX intraday).
      IEX is a subset of the tape. During the session a "live"
      price can print far from NBBO and Chg% looks like a bug.
      Document it, or allow feed=sip via secret for paid keys.

P2-4  APEX intraday still requests adjustment="split"
      while daily history uses "all". Split-only vs split+dividend
      will disagree with the daily APEX score on the same name
      around ex-div. Use "all" everywhere.

P0-adjacent: Alpaca snapshots
      r.json() is iterated as {symbol: snapshot}. Confirm against
      the live schema; some Alpaca versions wrap under "snapshots".
      A schema change returns {} and live update silently shows
      "unavailable" for every row.

P2-5  Dump URL is a public GitHub raw file, timeout=120, no retry.
      First Cloud visitor pays the gzip JSON → 5700-name panel
      parse. If GitHub is slow the request dies and — if no local
      npz — Top 20/Lookup/APEX raise. After the first success the
      npz is on disk (until the replica dies).

      Recommend: retry 3x with backoff; stream to disk; show a
      progress caption; consider committing a starter dump_panel_v4.npz
      so cold start is a 4-day-stale scan rather than an error.

P2-6  mega_scan RSI/MACD still run ewm/rolling on the full T×~5700

      (matrix over the whole dump). Last ~240 rows would match
      last-bar RSI/MACD. Cut the window.
